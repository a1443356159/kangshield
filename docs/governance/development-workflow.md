# 开发与证据治理流程

状态：Active v2.0
更新时间：2026-08-08

## 变更顺序

1. 先更新需求、有效决策或里程碑。
2. 冻结契约、配置、失败状态和测试矩阵。
3. 实现最小切片。
4. 运行单元/契约测试和必要的真实或回放验证。
5. 报告进入 `docs/evidence/`，现行结论回写 `current-status.md`。
6. 确认代码、配置、文档与证据摘要一致后再提交。

## 文档职责

| 目录 | 内容 | 是否表达当前状态 |
|---|---|---|
| `design/` | 当前需求、架构、数据流、指标算法和模型选择 | 是 |
| `governance/` | 状态、决策、里程碑和发布门 | 是 |
| `device-data/` | 设备事实、协议和采集门 | 是 |
| `evidence/` | 某次运行的不可变报告 | 否；只表达当时证据 |
| `references/` | 用户提供的源材料 | 否；需经设计文档解释 |

## 证据规则

- E1 不得写成真机能力；单次 E2 不得写成长稳或可重复 E3。
- 受控 HTTP 故障不等于 RTSP、丢包或真实断线恢复。
- 公开数据结果不等于 C6c 目标域准确率。
- 工程工具通过不等于许可证、分发或临床有效性通过。
- 历史 evidence 不自动更新；当前状态只在治理文档维护。

## 验证命令

- `.venv/bin/python -m pytest -q`
- `bash -n scripts/slurm/runtime.sh scripts/slurm/*.sbatch`
- `git diff --check`
- 检查所有本地 Markdown 链接和需求/架构/决策/里程碑口径。

## 隐私与提交

- run 根和子目录 `0700`；JSON/JSONL、stdout 和敏感报告 `0600`。
- 端点从环境变量注入，不进入命令历史、manifest 或日志。
- 设备序列号、姓名、token、签名 URL、原始健康值和敏感媒体不得进入 Git。
- 提交前确认无凭据、范围与里程碑一致、Schema/配置/测试同步且新声明有对应证据。
